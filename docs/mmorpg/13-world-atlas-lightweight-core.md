# 第二模块｜World Atlas 轻量核心（2026-11-21，最高优先级）

> **这是当前第二模块开发的最新裁决。若与 10～12 或更早设计冲突，以本文为准。**
>
> 第二模块不是“专业知识图谱数据库”，也不是把小说运行时 Reality 的复杂事实模型提前搬进原生母体世界。它首先是一个**面向长篇小说作者与 LLM 的世界资料卡片库**。

> **世界内容层补充：** 本文规定“怎样存”，[14：World Atlas 世界内容框架 v0.1](14-world-atlas-content-framework-v01.md)规定“一个完整世界应该有什么”。v0.1～v0.7 现在被解释为 Content Schema，而不是要求增加 SQL 表的 Database Schema。

## 0. 一句话定义

**原生母体世界 = 可长期编辑的文字卡片 + 有语义的卡片链接 + 可重建的关系索引/图谱。**

作者看到并维护的是完整资料卡；程序与 LLM 从卡片中的语义链接得到结构化关系；关系图只是索引的浏览方式。

```text
世界卡片（资料真相）
      ↓
typed wiki links / 关系字段
      ↓
可重建 source_relations 索引
      ↓
反向关系 / 筛选 / 一跳多跳 / 图谱 / LLM 查询
```

## 1. 第二模块当前只锁定三个核心能力

### 1.1 世界卡片

人物、组织、地点、能力、物品、事件等都可以是一张完整文字卡。

- 卡片必须能自由写长文字，不要求把世界拆成大量严格字段。
- 卡片类似 M03 组件：内容首先服务作者和 LLM 阅读。
- 卡片可以有少量基础元数据：稳定 ID、名称、别名、类型。
- Markdown / 富文本正文是主要内容载体。

示例：

```markdown
# 旗木卡卡西

木叶上忍，第七班指导上忍……

所属组织：[[木叶隐村]]
老师：[[波风水门]]
学生：[[漩涡鸣人]]、[[宇智波佐助]]、[[春野樱]]
拥有：[[写轮眼]]
掌握：[[雷切]]
```

### 1.2 有语义的链接

普通 `[[宇智波佐助]]` 只说明“有关”。

第二模块需要保留“为什么有关”：

```text
卡卡西 ─老师→ 波风水门
卡卡西 ─学生→ 鸣人
卡卡西 ─所属→ 木叶
卡卡西 ─拥有→ 写轮眼
```

可以采用 Breadcrumbs 式 typed links / typed frontmatter，也可以在正文关系字段中识别 `关系名：[[目标]]`。

核心要求：

- 关系连接稳定卡片身份，而不是复制另一张卡。
- 能从 A 的关系自动在 B 上看到反向关系。
- 反向关系是查询/显示推导，不要求重复写两份事实。
- 未解析链接不应阻止卡片保存；后续卡片创建后可重新索引。

### 1.3 关系索引与图谱

关系索引是**派生数据**，不是第二份世界真相。

需要支持：

- 当前卡片的一跳关系。
- incoming / outgoing 反向查询。
- 按关系类型过滤。
- 按卡片类型过滤。
- 必要时二跳/三跳浏览。
- 关系图可视化。
- LLM 按实体和关系提取上下文。

索引损坏或规则升级时，应能从世界卡片重新构建。

## 2. 当前明确不做什么

以下能力不是原生母体 Atlas 的核心要求，不应继续扩大工程：

- 不需要 Neo4j 或独立知识图谱数据库。
- 不需要为每种关系设计“是否允许重复 / 是否允许自环 / 是否允许成环”等约束系统。
- 不需要关系事务规则、复杂 Relationship Metadata 或游戏平衡约束。
- 不需要把每个人物、能力、组织拆成大量强制结构字段。
- 不需要 Wikidata 式 Statement / Qualifier 体系。
- 不需要为了原生资料库实现 Event Sourcing、完整时态数据库或复杂 Reality Checkout。
- 不需要把正文结算后的动态状态模型复制到 Source World。
- 不因为未来小说剧情可能改变世界，就让原生母体卡片承担项目运行状态。

Migration 053 中已经存在的专业专项表属于历史实现资产。**不要删除已落地迁移，但不要把这些专项表继续当作第二模块完成度的中心，也不要强迫作者填写。** 当前 World Atlas 工作优先围绕卡片和关系索引展开。

## 3. 与 Project Reality 的边界

原生母体只描述参考世界：

```text
火影原生世界
├─ 卡片
├─ typed links
└─ derived relation index
```

小说项目真正发生的新事实仍由 NarraLume 原有 Canon / RelationshipEvent / Timeline / 正文结算链负责：

```text
Novel Studio 写正文
      ↓
事实确认 / 作者采纳
      ↓
Project Reality
      ↓
后续写作检索
```

**不要把 Project Reality 的复杂度提前污染 Source World。**

Source World 与 Project Reality 可以共享稳定映射，但二者职责不同。

## 4. 现有底座直接复用

不换 NarraLume，不另起数据库。

当前已有：

- `source_records`：世界卡片的稳定身份、名称、类型、别名。
- `source_world_lore_sections`：可以承载完整卡片文字。
- `source_relations`：正好作为 typed link 的派生关系索引。
- SQLite：足够支撑小说规模的几千至数万卡片和数万至十万关系。
- 现有 Web / API / 搜索 / 项目工作台：继续复用。

目标不是继续加表，而是把现有结构变成真正可用的 **World Atlas**。

## 5. 当前实现顺序

```text
A. 独立 World Atlas 工作区
      ↓
B. Source World / 卡片浏览与编辑
      ↓
C. [[wiki link]] 与 typed link 解析
      ↓
D. 保存卡片时重建该卡片的 outgoing source_relations
      ↓
E. incoming + inverse relation 查询
      ↓
F. 关系类型筛选 / 一跳多跳
      ↓
G. 关系图 UI
      ↓
H. 提供给 LLM 的 Atlas 查询接口
```

第一阶段验收不是“又增加几张表”，而是：

1. 作者能打开一个原生母体世界。
2. 能新建/编辑一张完整人物或世界卡。
3. 在卡片中写 `老师：[[波风水门]]` 等语义链接。
4. 保存后能从卡卡西查到水门，也能从水门反向看到卡卡西。
5. 能按“老师 / 学生 / 所属 / 能力”等关系过滤。
6. 图谱与 LLM 查询读取同一份派生索引。
7. 删除并重建关系索引后，卡片内容不受影响。

## 6. 对标项目只借这三层

- **SilverBullet**：卡片内容是资料真相；结构化关系索引可从文字重建。
- **Breadcrumbs**：typed links、有方向关系、implied/inverse relations。
- **Relations**：按关系类型查看、过滤和可视化。

不要因为对标项目还有其他能力，就把它们全部移植进来。

## 7. 防重犯红线

遇到第二模块 Source World 任务时，先问：

> 这项复杂度是在帮助“写卡片、连卡片、查关系”吗？

如果不是，而是在处理正文后的动态事实、剧情状态结算、关系约束、时态真值、游戏规则或数据库理论完整性，**立即停止并把它归回 Project Reality / Novel Studio 或未来专项，而不是继续扩 Source World。**
