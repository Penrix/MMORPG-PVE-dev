# 第二模块｜世界 Fork / Diff、人物人格锚点与 Reality Checkout（2026-11-20）

> 用户明确提出：**原生母体到项目世界可理解成 Fork；项目实际变化只看 Diff；原著人物的人设标签不应随着平行世界剧情随意改写，否则 OOC。**
>
> 本页是 [10：第二模块认知和错误纠正](10-module2-cognition-and-error-guardrails.md) 的最新补充。优先级：用户最新明确纠正 > 当前代码事实 > 旧设计结论。第一模块仍暂停。

## 重要的三层区别

```text
Source A / B / C：多个原生母体（资料基线、原著全文及完整历史）
          │
          │ Fork by SOURCE ID（不是按姓名拷贝出一整套人物）
          ▼
Project P：一本小说唯一的项目 Reality
          ├─ 不改动的母体资料：作为可查 Source Reference 继承引用
          ├─ 人物人格锚点：作者基于证据确认的核心标签与决策习惯
          ├─ Project Canon：真正发生并经过采纳的新事实与关系
          ├─ Timeline：项目事件顺序与各世界的本地时空
          └─ Diff = 指定源材料条目/字段基线 vs 当前有效 Project Canon
                   │
                   └─ Checkout：结合项目时间、位置、人物知识与历史分支
                              恢复当时真正成立的局部 Reality
```

**Fork 是引用和写时差异，不是“原著中未来所有事件无条件成为项目已发生的事实”。**
**Diff 是对原生资料的差异视图，不是另一套可写回的世界真相表。**
**Checkout 是查询投影，不是因为到了另一个世界而创建第二个小说项目。**

## 人物：不改内核，可以改变人生

人物的原著身份依据 `(corpus_id,source_key)`；项目身份依据 `(project_id,canon_entity_id)`，世界/地点和可能分支是人物所处的位置、事件坐标或实例。**名字只用于展示和检索，不充当身份键。**

### 不允许自动修改的人格锚点

对已有原著人物，明确保存有来源的人格内核，例如：性格母型、稳定性格标签、在压力下常见的判断习惯、珍视什么、怎样对待具体关系。至少包括由作者确认的 `tags` 与 `decisionPattern`，同一项目人物锚点**不可被日常剧情结算覆盖**。

不是把全世界同一人物都写成“冷静聪明重情”这样的泛词。更重要的是：既有标签实际怎样预测原著人物在具体压力、关系和环境中的选择。原著资料与测试示意必须严格区分，不能虚构原著标签。

### 可以因项目 Reality 改变的内容

- 实际年龄/身体状况、当前位置、职业身份、能力状态、资产与权限；
- 对他人的认识、感情、信任、敌意、关系和信息；
- 因长期经历改变的目标、处境、可选策略、已发生行为和人生轨迹；
- 原著未来尚未发生或已被小说改变的事件，以及实际社会和历史结果。

**角色没有按原著情节做出同样行动，并不自动 OOC。** 应检查是否存在足以改变该行动的新的现实条件；如果不存在，则是真正的人物偏离风险。

例：项目男主改变了宇智波鼬所知情报、与重要人物的关系及外部政治局面，鼬可能在保留其人格内核的同时作出原著未发生的选择。不能因“原著没有这段剧情”就把人物设为 OOC，也不能仅靠剧情需要让他忘记一贯判断习惯。

### 非原著人物与刻意重构

项目原创人物也有作者初始确认的人格锚点，`source_corpus_id/source_key` 可以为空；如果作者明确创作“同名不同人”或刻意改造原作人格，项目必须**显式标注为不同的人物身份/有意改编**，而不是让普通模型的剧情写回悄悄改原著人物标签。

## 第 051 迁移的实际范围

- `project_character_anchors`：一个项目人物一份作者确认的核心人格锚点，记录明确来源及决策模式。普通 SQL 更新/删除被拒绝，不能在写章节时不知不觉覆盖；并不自动分析出真实原著人格。
- `project_fork_claim_baselines`：**选择性、固定的原著字段快照**；建立映射时把已绑定 `source_records.raw_json` 的一个字段与本项目实际 `canon_facts.predicate` 关联，保留原始基线。在来源重新导入时基线不会暗中漂移。
- `SqliteProjectForkRepository.diffEntity`：读取原著基线 + NarraLume **已确认/已锁定、当前有效** 的项目事实，返回 `reference_inherited`、`same_as_source`、`project_changed`、`project_conflict` 和未映射的 `additions`。
- 数据库未发现项目已采纳事实时报告 `reference_inherited`，这仅是**参考基线未被覆盖**，不证明项目当前时点已经发生所有原作事实。
- HTTP API 位于 `/api/projects/:projectId/world-fork/:entityId` 等；`WorldEntityDossier` 继续使用已有 Canon/Lorebook/History，加出 `sourceForkDiff` 查询视图。

**当前只覆盖被明确映射的原著字段，并没有实现“全原著、一键语义化自动 Diff”。** 对忍术的深层规则、组织产权与人际关系需基于领域对象进行有证据的差异计算；没有映射不可误判为不存在或删除。

## 已发现但尚未解决的两个重要问题

1. **同名人物**：`canon_entities` 原生仍有 `UNIQUE(project_id,type,name)`；虽然 050 的身份已用 source ID 和 project entity ID、空间关联，不按名字判断，但这个旧约束仍阻止一个项目把不同世界同名者直接以同样 display-name 保存。这需要安全的数据库升级与界面消歧，**051 没有声称已修复**。
2. **真正的历史 Checkout**：原生 `listEffectiveFacts` 是全项目当前有效事实，没有实现按 `world_space + local_time + branch + event_sequence` 的版本查询；051 的 Diff 默认与**当前已采纳事实**比较。不能把它说成已经能恢复任意时间、任意分支的全部 Reality。下一步应从事实与关系的时间生效域及事件写回接口入手，而不是简单加一份世界快照 JSON。

## 最小验收

1. 项目火影人物鼬有稳定 `project_id/entity_id`，明确引用 Naruto 原著材料。其人格锚点、压力下判断习惯不因剧情变了而被普通写回替换。
2. 从原生资料选定属性如职位作为基线，项目没有实际变动时报告 `reference_inherited`，不伪造已发生的项目历史。
3. 项目已采纳的职位与原著不同，显示项目改动；项目新认识男主，显示关系新增；人格锚点维持不变。
4. 上游源记录更新，不允许静默改变项目的已固定比较基线。
5. 火影→楼兰过去→海贼→返回火影，仍沿同一项目 Canon 和人物 ID；不存在自动强制的世界复位或时间线分支。
6. 来自其他小说的同名角色不能偷连到本小说项目；同一项目里的跨世界同名存储问题仍须专项解决。

**底线：世界和人生可以越来越偏离原著，但人物应当是在这些新的现实条件下继续作为“他自己”行动。**
